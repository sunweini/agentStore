# 检索式构造：双轨三式与语法差异

## 分组原则：国别 × 项目群

不要写一条大而全的检索式。切分的理由是运营性的，不是美学的：

- **频次不同**：战乱区项目要小时级，低风险轻扫组月级就够
- **白名单不同**：赞比亚组配赞比亚域名，刚果组配法语域名
- **语种不同**：风险词必须跟着语种走
- **归因需要**：命中后要知道是哪个项目出事，才能派给对应的运营人

分组编号建议 Q0/Q1/Q2…，其中：
- **Q0 = 集团层**（跨国别，抓点名监测主体自身的报道）
- **Q1..Qn = 各区域项目群**，按国别聚，同国别内按项目群再分
- **最后一组 = 轻扫组**，把所有低风险、待证、边缘项目打包低频跑

## 三式结构

每组内部拆成三条式子，各司其职：

### a 全量轨
```
(实体键簇) AND (地域限定)
```
宽召回，用于掌握全貌、发现未预期的议题。频次可以低（周/双周），但不能不跑——只跑精准轨会让你只看得见已知风险类型。

### b 精准轨
```
(实体键簇) AND (风险词簇)
```
只抓负面，噪音低，**可以高频跑**。这是日常预警的主力。

### c 不点名轨
```
(地名键) AND (行业词) AND (外资标识词)
```
抓"发生在项目所在地、但报道里没点名"的负面。这类信号往往比点名报道早几天出现，是真正的早期预警。

命中结果通常落在 **context** 相关度层——纳入风险监测，但不计入主体自身负面指标。

不是每组都需要三式：
- 集团层通常只要 a + b
- 高风险区域组三式齐全
- 轻扫组一条 a 式即可

## 布尔语法 vs Google 语法

**两套必须都给，不能只给一套。** 爬虫走新闻 API / 舆情数据库时用布尔式；走搜索引擎抓取时用 Google 式。语法不通用，混用会静默失效（不报错，但结果是错的）。

主要差异：

| 项 | 布尔语法 | Google 语法 |
|---|---|---|
| 取反 | `NOT (a OR b)` | `-a -b`（每个词单独加减号） |
| 与 | 显式 `AND` | 空格即 AND |
| 或 | `OR` | `OR`（须大写） |
| 括号嵌套 | 支持多层 | 支持有限，深层嵌套会被静默忽略 |
| 词组 | `"..."` | `"..."` |
| 通配符 | `truncat*` 多数支持 | 基本不支持 |

写 Google 式的注意事项：

- **嵌套要压平**。布尔式里三层括号，转 Google 式时要拆成几条并列查询，或牺牲一点精度压成两层
- **取反逐词写**：`NOT (cricket OR minecraft)` → `-cricket -minecraft`
- **别太长**。Google 式过长会被截断，抓不到东西还不报错。核心实体保留 3–5 个，其余靠白名单收窄
- **通配符换成穷举**：`hydrometallurg*` 在 Google 式里要写成具体词或干脆去掉

## 常见干扰模式与对策

| 干扰类型 | 表现 | 对策 |
|---|---|---|
| 缩写撞体育/游戏 | 缩写命中赛事、俱乐部、游戏赛事，量级碾压真实信号 | X 层排除词 + context_guard 双保险 |
| 同系兄弟单位 | 名称仅一字之差的同行业集团 | 排除词逐个列出，含股票代码 |
| 本国内部信息 | 招采公告、人事、培训等国内业务信息淹没海外信号 | 母语检索式强制附加地域词，或爬虫侧按域名分流 |
| 通稿多站转载 | 同一条正面新闻被几十站转载，正面量虚高 | 抓取后 URL 归一化 + 正文相似度去重 |
| 历史报道混入 | 几年前的旧闻被重新索引 | 检索式带时间窗；旧报道仅用于确认项目背景，不计入统计 |

---

## 时间窗

常规设**最近 12 个月**统计窗。更早的报道可以抓、可以用于确认项目背景与历史先例（比如"施工期就发生过罢工"这类前科），但**不计入当期统计**，否则同比环比全乱。

历史先例很有价值，建议单独在运营注里记一笔，不占数据行。

## 检索式的验证

新写的检索式**不能直接上线**，尤其是小语种。验证方法：

1. 手工在目标搜索引擎/属地站点跑一遍
2. 看是否有召回（一条都没有，多半是词写错了或当地不这么叫）
3. 看噪音比例（噪音过半就要加 context_guard 或收窄白名单）
4. 抽查前 10 条，确认相关度分层符合预期

未经验证的一律在清单里标注（如 `⚠未做召回验证`），并把频次先设为低频，人工抽查后再提频。
