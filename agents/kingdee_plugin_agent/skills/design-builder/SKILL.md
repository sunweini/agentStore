# 金蝶插件设计方法论(design-builder)

配合 w2 设计阶段使用。系统提示已注入本 skill 摘要,LLM 需要完整设计方法论与
类型检查清单时调用 `load_skill("design-builder")` 获取本文与三套类型清单。

## 目标

基于 w1 需求确认摘要(spec 的 decisions/assumptions + subtask 的 title/plugin_type),
产出**一份可直接交给 w3 编码的插件设计文档**(design.md)。设计是"编码前想清楚",
不是流程形式主义 —— 每条设计决策都要能追溯到 w1 确认的决策或假设。

## 输入

- `requirement_spec`:w1 确认摘要(decisions 逐条决策、assumptions 用户未说的默认值、subtasks+deps)
- `subtask`:本子任务的 title(业务描述)与 plugin_type(bill/service/list)
- RAG 检索上下文:guide(按 plugin_type 过滤的团队指南)+ api_ref(API 参考片段)
  —— 字段/操作/事件签名引用必须来自元数据或指南,**禁止编造**
- 经验库检索上下文(experience):按子任务标题查历史踩坑,命中注入"历史踩坑参考"
  (verified 优先、仅供参考非必须满足)—— 已知错误模式要转化为设计规避,不是新增需求

## 流程步骤

1. **定类型与基类**:按 plugin_type 定基类 —— bill → `AbstractBillPlugIn`、
   service → `AbstractOperationServicePlugIn`、list → `AbstractListPlugIn`;
   类名/命名空间沿用子任务约定。基类写错,后续生成/审查/编译全部连锁失败。
2. **取类型检查清单**:按类型调取 `references/bill.md` / `service.md` / `list.md`,
   逐项落实清单,不允许"这段与本类型无关"跳过 —— 每项都要写明设计结论
   (包括"不涉及"的明确结论)。
3. **查历史踩坑(经验库)**:设计前先查历史坑 —— 按子任务标题检索经验库
   (seed + w7 沉淀),把已知错误模式转化为设计规避:如**签名级联** → 设计时
   核对基类事件签名(OnLoad/AfterDoOperation 等,对照 templates/<type>/template.cs
   基准),避免设计里写错签名让 w5 编译反复修;命中只作规避参考(verified 优先),
   不改变输出骨架、不引入新需求。
4. **事件绑定决策**(bill/list):确定挂载操作与时机 —— OnLoad 初始化、
   AfterDoOperation 操作后联动、操作前校验等;只挂 w1 确认的单一操作,
   多操作需求在 w1 已拆多子任务,不要在本设计里追加第二个操作。
5. **控件与字段映射**(bill/list):要操作的**真实字段**(选项来自元数据
   get_form_fields,如 FQty/库存组织),写明读写方向(读源字段 → 算 → 写目标字段)
   与控件状态变更(可见/可编辑)。
6. **拦截方式**(bill):校验不通过走硬拦截(抛异常,操作不提交)还是软拦截
   (仅提示/标记);**拦截提示文案必须写进设计**(w3 照抄,w4 对照审查)。
7. **联动单据**:是否读写其他单据(读库存单校验、生成下游单据等),写明目标
   FormId、写入字段、是否允许跨组织;拿不准的标进"边界与假设"。
8. **异常处理骨架**:插件异常(元数据/依赖服务不可用)的回滚策略、日志记录、
   是否通知审批人;try/catch 边界在设计中就划好,不要在编码时临场发挥。
9. **验收自检**:设计落盘前逐条对照 w1 的 decisions 与 assumptions
   (每条决策 → 设计对应小节;未覆盖的决策 = 设计缺陷,禁止带病交付)。

## 输出契约(design.md 固定骨架)

按以下结构输出,缺节视为不合格:

```
- 概述:目标单据/插件类型、要解决的业务问题
- 插件类设计:类名/基类、关键方法与事件覆写清单
- 核心实现要点:按类型清单(见 references/<type>.md)逐项落实
- 异常处理骨架:try/catch 边界、回滚/提示/日志策略
- 边界与假设:依赖的元数据项、权限/组织范围、未覆盖场景
- 验收自检:设计满足 w1 确认的每条决策与假设(逐条对照)
```

落盘前自检:类型要点全覆盖、引用真实字段/操作名(来自元数据),不许出现占位假字段。

## 踩坑与纪律

- **假字段 = 连锁灾难**:设计里编造 FXX 字段,会一路污染 w3 生成 → w4 审查 →
  w5 编译;字段/操作名一律以元数据为准,查不到就写进"边界与假设"待确认。
- **类型清单不是建议是检查项**:每项必须给出设计结论,"未涉及"也是结论,
  留空意味着 w3 无从下手、w4 无从审查。
- **一个操作一个设计**:单子任务只挂 w1 确认的单一操作,贪多会在 w3 模板冲突时
  被迫砍功能。
- **决策可追溯**:验收自检是设计质量的门槛 —— 无法对照 w1 决策的设计,
  退回 w1 重新确认,不要自己拍板新增业务规则。
