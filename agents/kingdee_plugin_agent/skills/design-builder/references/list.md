# 列表插件设计检查清单(list,基类 AbstractListPlugIn)

用法:逐项检查,**每项都要在设计文档中给出明确结论**("不涉及"也是结论)。
字段/按钮选项一律来自元数据 get_form_fields / get_operations,禁止编造。

## 1. 列表字段(必须)
- 列表要展示/管控的字段(来自元数据 get_form_fields):字段映射、列可见性、
  单元格只读/可编辑状态。
- 字段的计算/联动规则(哪列由哪列算出、何时刷新)。
- 检查自问:每个字段是否真实存在于元数据?只读/可编辑边界是否与业务语义一致
  (可编辑但无保存逻辑 = 设计缺陷)?

## 2. 操作按钮(必须)
- 列表操作栏按钮(来自元数据 get_operations,如审核/批量操作):按钮 → 动作映射。
- 批量选择时的**逐行处理语义**:每行独立校验还是整体校验?失败行怎么处理。
- 按钮可用条件:选中行状态过滤(如仅已审核行可操作)。
- 检查自问:按钮动作是否能在元数据中找到对应操作?批量场景的
  "部分失败"行为是否写明了?

## 3. 过滤条件(按需)
- 列表默认过滤条件:按组织/状态/时间过滤。
- 过滤参数来源:界面输入还是调用方传入;参数缺失时的默认行为。
- 检查自问:过滤字段是否真实?默认过滤是否会漏掉业务上必须可见的数据?

## 4. 批量异常处理(按需)
- 批量操作部分失败:**整体回滚**还是**逐行成功累积**?两者对数据的最终影响必须写清。
- 行级反馈机制(哪行失败、失败原因如何提示)与提示文案。
- 检查自问:逐行累积模式下,成功行与失败行的提示是否能让用户区分?
  整体回滚模式下,回滚前是否已有部分副作用需补偿?

## 5. 验收自检(完成设计时)
- 设计是否满足 w1 确认的**每条**决策与假设(逐条对照,列对应小节)?
- 是否出现 w1 未确认的新规则(出现 = 退回 w1 或标进边界与假设)?
