# 服务插件设计检查清单(service,基类 AbstractOperationServicePlugIn)

用法:逐项检查,**每项都要在设计文档中给出明确结论**("不涉及"也是结论)。
服务名/参数签名引用自元数据或指南,禁止编造。

## 1. 服务入口(必须)
- 业务服务类的标识(元数据中的服务名/类名)、暴露的服务方法与参数签名。
- 调用入口约定:FormId + 业务对象标识(服务被触发所依附的单据操作)。
- 检查自问:服务方法名与参数是否与元数据一致?入参来源(单据字段/调用方传入)
  是否写清?

## 2. 事务边界(必须)
- 事务从哪里开始、到哪里提交:**单操作内**还是**多步跨操作**?
- 读-判-写是否同一事务;事务超时与并发(锁)策略。
- 检查自问:事务边界与业务语义是否匹配(校验 + 提交不可分离时必须在同一事务)?
  长事务是否已评估锁冲突风险?

## 3. 异常回滚(必须)
- 业务异常与系统异常的分界,各走什么处理路径。
- 回滚点:哪些操作在异常时回滚、哪些已提交不可回滚(需补偿)。
- **部分成功时的补偿动作**:明确列出,不能只写"回滚"二字。
- 日志与提示文案(用户可见文案要写进设计)。
- 检查自问:是否存在"前几步已生效、后几步失败"的中间态?中间态的补偿/提示是什么?

## 4. 调用方契约(必须)
- 服务被谁调用:单据插件 / 列表操作 / 外部接口 —— 写清调用方。
- 调用方上下文(组织/权限)如何传入与校验。
- 返回结果的契约:成功/失败码 + 消息结构(w3 照此实现,w4 对照审查)。
- 检查自问:返回契约是否具体到 w3 能直接写代码(字段名/类型/失败码枚举)?

## 5. 验收自检(完成设计时)
- 设计是否满足 w1 确认的**每条**决策与假设(逐条对照,列对应小节)?
- 事务/回滚/返回契约三件套是否都写清了结论?
