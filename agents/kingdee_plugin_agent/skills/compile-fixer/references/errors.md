# 编译错误修复方法论(errors.md — 纯方法论)

用法:收到 compile_errors 后,**先把每条错误按下列分析维度归类,再按根因分析方法
定位源头修复**。本文件只含方法论 —— 错误分类框架、根因分析方法、经验库检索策略、
修复纪律,**不含任何具体错误映射**。

> **具体错误映射见经验库**(启动种子 `seed/compile_errors.json` + w7 运行沉淀),
> 由 w5 每轮按错误码+消息语义 `search_related` 检索后附注到 compile_errors
> (experience 字段)。**新踩坑不写这里,走 w7 沉淀进经验库**(proposed → verified
> 两态),避免静态列表与动态经验库双份维护、内容漂移。

## 一、错误分类框架(分析维度,不是错误码表)

收到错误先归类 —— 分类错了修法就错了。按"判断自问"归类,不靠记忆错误码:

| 维度 | 判断自问 |
|---|---|
| A. 缺引用/命名空间 | 类型名/命名空间"找不到"?先区分"类型是否真实存在"与"是否被引用"两件事,再补 using / 程序集引用 |
| B. 签名与基类不匹配 | 错误指向重写/事件方法?参数类型/个数/返回类型与基类声明是否逐字一致? |
| C. 拼写与作用域 | "名称不存在/成员不存在"?是拼写错、作用域外引用,还是名字本身编造(元数据查不到)? |
| D. 语法与占位符残留 | 分号/花括号/语句结构错误?模板渲染后结构是否被破坏、占位符是否残留? |

同一批错误可跨多个维度;先逐条标维度,再进入根因分析。

## 二、根因分析方法(从错误定位根因)

1. **区分表象与根因,找源头**:一条根因(如签名不匹配)会引发一串下游错误
   (方法调不到 → 成员不存在 × N)。修根因,不要逐个"修"下游表象。
2. **签名错误是级联源**:错误列表同时出现"签名/重写类"与"成员不存在类"时,
   优先核签名 —— 签名对齐后下游错误通常批量消失(级联消错)。
3. **阻断性优先**:缺引用/命名空间与签名类是阻断性错误(一条修好消一片),
   先修;拼写/作用域是单点错误,后修;语法/残留收尾。
4. **不确定的名字不编造**:名称不在元数据/API 参考里 = 编造,必须换真实名
   (字段来自 get_form_fields,操作来自 get_operations)。
5. **对照模板与规范**:签名、using 集、命名空间路径以 `templates/<type>/template.cs`
   与金蝶 BOS API 规范为准,不凭记忆写参数类型/成员名。

## 三、检索策略(如何查经验库)

具体错误映射的**单一来源是经验库**(启动种子 + w7 沉淀),w5 每轮失败已自动
按错误码+消息语义 `search_related` 检索并附注:

1. **命中**(experience 附注非空)→ 直接按建议修复并**自核**:附注可能与当前
   代码上下文不符,标注 `confidence=verified` 的优先采用;`unverified`
   (proposed 态)条目必须核实上下文后才采用。
2. **未命中** → 按本文件方法论(分类 + 根因分析)+ BOS API 规范自行修复;
   "经验未命中"不是拒绝修复的理由。
3. 修复后把仍然踩到的坑留给 w7 沉淀进经验库(自动完成,无需人工登记)。

## 四、修复纪律

1. 每轮至多 5 轮(MAX_COMPILE_ROUNDS):轮内顺序 "分类 → 根因 → 检索 → 修复 →
   写回重编"。
2. **禁止重复提交相同代码**:每轮必须真实改写才写回重编(上层有防原样重提交
   校验,但每轮都应给出真实修改)。
3. **修复后必重编**:写回后交由编译容器重编验证,不自行宣称"应该能过"。
4. 每轮只处理本轮错误,不重构无关逻辑,防级联误判。
5. 不为消错删除功能代码(删功能是最后手段且要上报;宁可编译超限退回 w3/w4)。
6. 编译服务不可用(BLOCKED)不计轮次、不扣预算,不要为了"过编译"删功能。
