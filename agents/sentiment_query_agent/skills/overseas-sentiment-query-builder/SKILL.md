# 海外舆情检索任务清单构建

把"我们要监测这家企业的海外负面舆情"这种模糊需求，变成爬虫今晚就能跑起来的任务表。

核心产出是一份多 sheet 的 Excel：**检索任务清单**（每行一个爬取任务）+ **关键词字典**（分层词表与消歧规则）+ **调度说明**（运营纪律）。

## 为什么这么设计

舆情监测最常见的两种失败，都不是技术问题：

1. **召回不足**——只用集团名检索。母公司名、海外法人名、项目地名、设施名都不进词表，结果一场溃坝诉讼、一次罢工完全抓不到，因为当地媒体从来不写集团名，只写当地法人和地名。
2. **信噪比崩溃**——词表一放开，短缩写（LCS、CCS、CNMC）和同名干扰（缩写撞上体育赛事、游戏、同名集团）灌进来，运营被淹没后干脆不看了。

这套方法用**分层词表**解决第一个问题，用 **context_guards + 排除词 + 属地域名白名单**解决第二个问题。两者必须同时做，只做一个都会失败。

## 工作流

### 第 1 步：厘清监测主体与口径

先把这几件事问清楚或从已有材料中提取，**不要跳过**——口径错了后面全白做：

- **监测主体是谁**：法定全称、常用简称、英文名及其拼写变体
- **主体在项目中的角色**：是业主还是承包商？这决定了相关度分层怎么定义
- **同名干扰源**：有哪些同名/近名的其他实体会污染检索

角色问题尤其重要。如果监测主体是**承包商**，那么业主方（往往是关联公司）的负面舆情对它属于"传导风险"而非"自身负面"，统计时必须分层，否则给客户的负面指标会严重虚高。

据此定义三级**相关度**（沿用这套口径，除非用户另有要求）：

| 相关度 | 含义 |
|---|---|
| direct | 点名监测主体自身，或其在场承包的项目 |
| indirect | 未点名，但可确定指向该集团/关联实体的项目 |
| context | 行业性报道，仅称"中国企业/外资企业"或涉他企，未指向具体公司 |

### 第 2 步：建分层关键词字典

按 A/B/C/D/R/X 六层拆词。**分层不是为了好看，是因为每层的检索行为不同**——实体键可以单独跑，风险词只能作为 AND 条件，排除词全局附加。

详见 `references/keyword-dictionary.md`（分层定义、context_guards 生成规则、人名键处置）。要点：

- **A 实体键**：集团名簇 / 海外法人簇（按语区分组）/ 关联集团层。海外法人名是召回率的命脉
- **B 地名·设施键**：矿区、厂区、水系、路段、行政区。当地媒体报道事故时往往只写地名
- **C 人名键**：**默认停用**。人名检索易引入隐私与误伤风险，须人工审核后逐条启用，转写未经验证的一律不启用
- **D 产品/业务键**：产品名、矿种，用于补充召回
- **R 风险词**：分语种维护，只作为精准轨的 AND 条件，不单独跑
- **X 排除词**：全局附加，专治同名干扰

**context_guards 是关键机制**：任何 ≤5 字符的缩写都必须强制 AND 一组限定词，否则必然引入噪音。字典里要单列一栏写清楚。

### 第 3 步：按"国别 × 项目群"分组，写双轨三式检索式

不要写一条大而全的检索式——无法排频次、无法配白名单、命中后无法归因。按**国别 × 项目群**切成组（Q0 集团层、Q1..Qn 各区域组），每组内部再拆成三式：

| 轨 | 构成 | 作用 |
|---|---|---|
| **a 全量轨** | 实体键簇（+ 地域限定） | 宽召回，掌握全貌 |
| **b 精准轨** | 实体键簇 AND 风险词 | 只抓负面，可高频跑 |
| **c 不点名轨** | 地名键 AND 行业词 AND 外资标识 | 抓同区域未点名的负面（context 层） |

每式同时给 **布尔语法** 和 **Google 语法** 两个版本——爬虫走 API 用布尔式，走搜索引擎抓取用 Google 式，两者的取反和括号规则不同，不能混用。语法差异见 `references/query-patterns.md`。

### 第 4 步：配属地信源白名单

**这是决定信噪比的一步，也是最容易被略过的一步。** 国际大媒体（路透、行业媒体）只报大事；真正的早期信号在属地媒体、当地法律数据库、政府部门网站、NGO 报告里。

每组配一份域名白名单，按国别整理。类型上要覆盖：属地主流媒体、调查报道媒体、行业垂直媒体、法律/司法数据库、政府主管部门、国际 NGO 与人权机构。方法与筛选标准见 `references/source-whitelists.md`。

对信源要做**可信度标注**：单一信源、AI 生成内容站点、明显立场媒体，都要在清单里标出来，要求交叉验证后才可引用。

### 第 5 步：定频次与风险等级

频次不是拍脑袋，按下面的信号定，详见 `references/cadence-and-risk.md`：

| 频次 | 适用 |
|---|---|
| 快讯/小时级 | 涉人员安全（战乱区、治安事件、伤亡） |
| 日级 | 进行中的司法程序、政治敏感期、已发酵的重大事件 |
| 周级 | 常规核心项目组 |
| 双周/月级 | 轻扫组、低风险区域 |

需要提频的信号：所在国大选年、项目投产/复产等高曝光节点、诉讼进入更高审级、当地战事或治安恶化、议题已外溢到国际媒体或学术圈。

### 第 6 步：生成 Excel

把上面的成果写成一份 JSON spec，然后用脚本生成：

```bash
python scripts/build_task_xlsx.py <spec.json> <输出路径.xlsx>
```

spec 的字段结构见 `assets/task_spec_example.json`（可直接复制修改）。脚本负责三个 sheet 的生成、频次与风险的色标、列宽冻结与筛选器——这些是确定性的重复劳动，交给脚本比手写 openpyxl 可靠。

生成后**务必打开确认**行数与分组无误，再交付。

## 分步脚本使用指南(流水线模式)

本 skill 提供 **6 个分步脚本**(`scripts/step1_entities.py` … `step6_cadence.py`),供 AI Agent 流水线逐步调用——每步由 Agent 完成「联网搜索 → LLM 生成」后,调对应脚本把结果**按固定格式标准化**,再进入下一步。这是与「一次性生成 Excel」并行的第二种使用方式。

### 调用约定

每个脚本:**读 stdin JSON → 校验/标准化/补默认/记 GAP → 写 stdout JSON**。

```bash
echo '<JSON>' | python3 scripts/stepN_xxx.py
```

- 脚本只接受 stdin JSON,不接受命令行参数
- 输出 stdout JSON;若输入不是合法 JSON 或字段缺失,退出码非 0 + stderr 输出 `FORMAT_ERROR: <原因>`
- 字段缺失/非法值:自动补默认值,并以 `GAP00N` 编号记录到输出的 `_gaps` 字段(不中断流程)

### 脚本与步骤对应

| 脚本 | 对应步骤 | 标准化内容 |
|---|---|---|
| `step1_entities.py` | ① 实体测绘 | 母公司/子公司/海外法人(语区分组)/拼写变体/同名干扰源 |
| `step2_profile.py` | ② 主体画像 | 角色(承包商/业主/ai判定)+ 相关度口径 + 重点地区 |
| `step3_keywords.py` | ③ 关键词字典 | A/B/C/D/R/X 六层行(短缩写强制 context_guard) |
| `step4_queries.py` | ④ 双轨检索式 | schemes×tracks,布尔+Google 双语法(轨 key 限 a/b/c/快讯/司法/招标) |
| `step5_sources.py` | ⑤ 属地信源 | 每轨 sources[](域名白名单,自动去协议/路径/转小写) |
| `step6_cadence.py` | ⑥ 频次定级 | 每轨 frequency/risk/relevance(快讯轨强制快讯/小时级) |

### 步骤间数据流

```
step1 → step2 → step3 → step4 → step5 → step6
实体测绘  画像   关键词   检索式   信源   频次定级
  └──── 逐步传递,每步产物作为下一步输入 ────┘
```

- step4+5+6 的 `schemes` 结构一一对应:step4 建轨,step5 补信源,step6 补频次风险,逐步合并
- step3 的 `keywords` 即最终 spec 的 keywords 行,无需再转换
- 每步输出的 `_gaps` 需收集汇总,写入最终交付物的「待补缺口」

### 输出格式契约

6 步输出的**唯一格式定义**在 `references/output-formats.md`(每步 JSON schema + 字段枚举)。**Agent 每步的提示词必须引用该文件**,LLM 按 schema 输出,脚本负责兜底校验。

## 输出规格

**Sheet 1「检索任务清单」**（核心）——每行一个爬取任务，12 列：

```
任务ID | 检索组 | 国家/地区 | 语种 | 检索式(布尔) | 检索式(Google语法)
     | 目标信源白名单(域名) | 建议频次 | 风险等级 | 命中期望相关度 | 状态 | 运营注/说明
```

「状态」列留给运营勾选（待启用/运行中/暂停），频次与风险等级用色标区分优先级。

**Sheet 2「关键词字典」**——6 列：层 / 键类别 / 关键词与别名 / 语种 / context_guard / 排除词与备注。

**Sheet 3「调度说明」**——用途、色标释义、双轨三式结构、去重规则、噪音隔离、单一信源标注、待补缺口、相关度口径。

## 必须写进交付物的运营纪律

这几条是踩过坑才有的，生成清单时要写进「调度说明」sheet，不能省：

- **去重**：企业通稿会被多站转载，抓取后须做 URL 归一化 + 正文相似度去重，否则正面量级虚高，指标失真
- **本国噪音隔离**：中文/母语检索式必须附地域词或按域名分流，否则国内招采、人事、培训信息会把海外信号稀释掉
- **单一信源标注**：只有一个来源的事件，引用前必须交叉验证；自述 AI 撰写的站点不得作为独立依据
- **数据缺口登记**：拼写未证、实体名缺失、某语种召回未验证的，都要明确登记为 GAP 编号并写进清单，避免后续误以为"已覆盖"
- **未验证检索式标注**：机器生成但没做过召回验证的检索式（尤其是小语种），要标注为待验证，启用前人工抽查

## 常见错误

- **只用集团名建词表** → 属地报道全部漏抓，这是最致命的
- **短缩写不加 context_guard** → 噪音淹没运营
- **不区分 direct/indirect/context 就合计负面数** → 把关联公司的负面算成客户自己的，指标严重失真
- **不配属地白名单，只搜大媒体** → 只能事后追热点，失去早期预警价值
- **承包关系不核实就入表** → 把别家公司的项目算进来，稀释真实风险信号；每个项目的总包方都要有依据
